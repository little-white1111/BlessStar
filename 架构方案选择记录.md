# 🏛️ 架构方案选择记录 (ADR) — 全链路接通

## 1. 需求背景

打通 **Editor（Electron 前端）↔ 配置文件（JSON）↔ 业务系统** 的完整链路。当前瓶颈：

* AI 管线 1400+ 行 `pipelineManager.ts` 硬编码 BlessStar 领域逻辑，无法复用到其他配置领域

* 配置编辑只有"内部管理"模式，缺少项目级别的导入/导出/分发工作流

* 没有统一的工作区概念来管理多环境、多格式的配置文件

* Editor 侧 AI 操作无法直接映射到业务系统可消费的配置文件变更

**核心目标**：先实现一条完整的「AI 编辑 → 配置文件生成 → 业务系统消费」链路，验证架构可行性，再逐步扩展。

***

| **维护成本**      | ⭐（短期低，长期高 — 技术债累积）                                        | ⭐⭐                                           | ⭐⭐⭐（前期高，但长期分摊）                                                                      |
| **领域可扩展数**    | 1 个（BlessStar 自身，硬编码）                                     | 2-3 个（注册表模式上限）                               | **N 个**（Plugin 注册制，无上限）                                                             |

### ⚙️ 架构不变量（审查红线）

1. **双向依赖禁止**：`ai-engine-core` → `IDomainPlugin`（引擎调用接口），禁止 DomainPlugin 反向 import 引擎内部状态或直接操作 DOM
2. **Workspace 数据主权**：所有配置文件的读写必须经过 `bs_workspace_*` C ABI，禁止 Editor 直接调用 `fs.writeFile` 写入 `src/` 目录
3. **Plugin 隔离性**：每个 DomainPlugin 运行在自己的命名空间下，禁止跨 Plugin 直接访问对方注册的 tool 或 state
4. **全链路 TraceID**：从 Editor 的 AI 操作到 Kernel 状态变更，每次调用链必须携带 `traceId`（UUID v4），记录到 ExecutionTrace 和 WAL audit log
5. **格式转换双向幂等**：`v1_json ↔ yaml ↔ toml ↔ ini` 转换必须是 round-trip 安全的 — 任意转换两次回到原格式后，语义等价（允许格式化差异，不允许字段丢失）
6. **Workspace 元数据一致性**：`.blessstar/` 目录必须时刻与 `src/` 内容一致。如果检测到 `src/` 文件被外部修改，必须重新扫描并更新 `.blessstar/schema/` 和 `.blessstar/workspace.yaml`
7. **AI 管线执行可观测**：每次 Pipeline 执行必须在 `ExecutionTrace` 中记录 `{traceId, stageName, duration, toolCalls[], status}`，可通过 `window.blessstar.getTrace(traceId)` 查询
8. **门控不可绕过**：从 Workspace 写入的任何配置变更，在写入 Kernel state 前必须经过 Gate Chain 校验。绕开门控的写入路径（如直接写 SHM）视为违规
9. **Plugin 版本契约**：`IDomainPlugin.version` 必须与 `PipelineEngine` 声明的 `supportedPluginVersion` 匹配，不匹配的 Plugin 拒绝加载

interface IDomainPlugin {
  id: string;                   // "blessstar" | "myapp"

  // 领域数据
  tools: IToolDeclaration[];

# 🏛️ 架构方案选择记录 (ADR) — workspace 加固

## 1. 需求背景

当前 workspace 使用**裸文件 I/O**（`std::ifstream`/`std::ofstream`）读写配置文件，存在以下风险：

* **崩溃不安全**：`bs_workspace_write` 在写入中途崩溃 → 磁盘遗留半截文件，无可恢复手段

* **无版本追踪**：每次写入覆盖原文件，无法回退到历史版本

* **无 fsync 策略**：操作系统可能延迟刷盘，断电后数据丢失

* **与 WAL 持久化脱节**：`adapter/persistence/` 已有完整的原子写入 + WAL + 崩溃恢复 + 版本管理能力（`BsAttachStore`），workspace 未利用

## 2. 三大候选方案对比

| 维度           | 方案A (裸 I/O 加固)                          | 方案B (直接路由 Store)                                                | 方案C (可插拔存储后端) ⬅️ **已选中**                                          |
| :----------- | :-------------------------------------- | :-------------------------------------------------------------- | :---------------------------------------------------------------- |
| **核心思路**     | 原地改为 `FlushFileBuffers`/`_commit` fsync | `bs_workspace_read/write` 直接调用 `BsAttachStore::commit_per_path` | 新增 `StorageBackend` vtable 抽象，两个实现：`LocalDirect` + `PersistStore` |
| **崩溃安全**     | ❌ 低级（仅 fsync，无原子写）                      | ✅ 高级（WAL + epoch）                                               | ✅ 按后端选择                                                           |

### ⚙️ 架构不变量（审查红线）

1. **存储后端透明性**：`bs_workspace_build` / `bs_workspace_export` 等上层操作**不得感知**当前使用的 StorageBackend 实现；所有存储调用必须通过 `ws->storage->read/write`
2. **错误码统一**：两种后端必须对相同语义条件返回相同错误码（`-ENOENT` 对文件不存在，`-EIO` 对 I/O 失败等）
3. **路径安全**：`StorageBackend` 必须拒绝 `..` 路径穿越（path traversal），禁止访问 workspace root 之外的任何文件
4. **测试无侵入**：`BS_TESTING` 宏或 `BSTORAGE=local` 环境变量自动启用 `LocalDirectStorage`，现有 7 个 workspace 测试无需任何修改
5. **生产默认**：无 `BS_TESTING` 且无 `BSTORAGE` 覆盖时，默认使用 `PersistStoreStorage`
6. **不变量 #2 不削弱**：即使使用 `PersistStoreStorage` 后端，所有配置文件的读写仍然必须经过 `bs_workspace_*` C ABI（不变量 #2），禁止绕过 workspace 直接调用 `BsAttachStore`

# 🏛️ 架构方案选择记录 (ADR) — 持久化与通信修复

## 1. 需求背景

当前 Editor ↔ 配置文件 ↔ 业务系统链路存在 3 个已确认的架构级问题：

1. **双写分歧**：`commitBatch` 写入 `ConfigManager` (kernel state) 时不更新 `runtime_values`，`AI write_config_value` 同时更新两者，两条写入路径不同步。`bs_config_read(key)` 读到的是旧值。
2. **冷启动值丢失**：`configPersistLoadFfi` 已加载 `configs.json` → `runtime_values`，但 Editor UI 启动时 `formValues = {}`，从未向后端查询实际值。用户重启后表单空白，只显示 Schema 默认值。
3. **三层持久化真相不明**：`configs.json`（persistWrite）、WAL（BsAttachStore）、workspace `runtime.json`（方案A同步桥）三者写入时机不同，无层级契约，崩溃后可能不一致。

核心目标：统一写入路径，确保（冷启动后读取可回放的最新值、修改配置后只重拉变更的单个值、持久化经过 WAL）。

## 2. 三大候选方案对比

| 维度 | 方案A (极简运维) | 方案B (性能优先) | 方案C (高扩展) |
| :--- | :--- | :--- | :--- |
| **核心思路** | commitBatch handler 尾部追加 `writeBlessStarConfig` + 启动时 `config:init` IPC 全量推送 | commitBatch C ABI 内部直接写 `runtime_values`，消除尾部补写；冷启动用增量 `list_configs` 按需拉取 | 定义三层存储层级契约（WAL=真相 → configs.json=缓存 → workspace=导出），引入 epoch 版本校验确保一致性 |

### ⚙️ 架构不变量（审查红线）

1. **写入路径唯一性**：所有配置变更必须经过 `config_commit_batch_c()` + `bs_config_write()`，禁止只写其一的分歧路径。`writeBlessStarConfig` 不得单独调用。
2. **冷启动值可回放**：Editor 启动后 `formValues` 必须反映 `runtime_values` 已持久化的最新值，不得为 `{}`。
3. **持久化层级契约**：WAL（`BsAttachStore`）= 系统真相（System of Record），`configs.json` = 写时复制缓存（Cache），workspace `runtime.json` = 用户可读导出（Export）。上层组件不允许跳过 WAL 直接写 `configs.json`。
4. **增量更新原则**：修改单条配置后，只拉取该条配置的当前值，不允许全量重拉。`subscribeWatch` 每次只推送一个 `{key, value, epoch}` 增量事件。
5. **版本有序**：写操作必须携带 epoch 版本号。`ConfigManager` 只接受 `current_epoch + 1` 的写入，拒绝乱序 (`ESTALE`)。`configs.json` 文件头携带 `epoch` 元数据。
6. **崩溃可恢复**：启动时 `configs.json.epoch < WAL.epoch` → 自动从 WAL 重放缺失条目 → 重写 `configs.json`。不允许静默加载过期缓存。
7. **Watch 不阻塞**：`subscribeWatch` 使用 eventfd 异步通知，禁止在 Watch 回调中执行同步 I/O 或长耗时操作。

export function useConfigWatch() {
  const [values, setValues] = useState<Record<string, string>>({})
  const [isWatching, setIsWatching] = useState(false)
  const [error, setError] = useState<string | null>(null)

    })

      try {

        // data = { key, value, epoch }
        setValues(prev => ({ ...prev, [data.key]: data.value }))
      } catch { /* ignore malformed */ }
    })

    return () => { unsub?.() }

# 🏛️ 架构方案选择记录 (ADR) — 业务系统目录设计与配置注册规范化

## 1. 需求背景

当前 `Bussiness System/` 是外部目录，无固定结构、无自动注册机制。业务系统接入依赖手动调用 `BusinessAdapterRegistry.register()` (TS) 和 `bs_normalizer_register()` (C)，存在以下问题：

* **不可发现**：新人接入需翻阅文档才知道注册入口，无目录级契约感
* **胶水代码**：每个业务系统重复写 `getFieldDeclarations()` / `getAIData()` 等注册调用
* **无统一管理**：字段声明、AI 元数据、归一化器各自注册，无统一入口和结构保障
* **版本兼容不可控**：业务系统依赖的 SDK 版本无声明，升级可能静默破坏

**核心目标**：定义业务系统目录结构契约，实现配置声明和元数据的自动注册，最小化业务接入胶水代码。

## 2. 三大候选方案对比

| 维度 | 方案A (极简主义) | 方案B (性能优先) | 方案C (弹性扩展) |

### ⚙️ 架构不变量（审查红线）

1. **禁止业务代码侵入框架核心**：`business/` 目录不可反向依赖 `kernel/` 内部符号，仅可依赖 `app/sdk/include/` 公共 API 和 `adapter/include/` 公共接口。
2. **目录结构契约必须自动可发现**：不允许人工维护业务系统注册列表。`business/<biz_id>/manifest.json` 存在即视为注册意图，框架启动/编译时自动发现。注册内容包括：字段声明 (`fields`)、AI 元数据 (`ai`)、归一化器 (`normalizer`)、门禁 (`gate`)。
3. **隔离性**：一个业务系统的编译失败或运行时崩溃不可影响其他注册的业务系统。动态插件模式下，crash 不可波及主进程。
4. **版本兼容声明**：`manifest.json` 必须声明兼容的 SDK 版本 (`sdk_version`)，格式为 semver range (如 `">=1.0.0 <2.0.0"`)。不兼容时启动时拒绝加载并报明确错误。

// ── app/editor/src/ai/business-adapter/bridge.ts (新增) ──

/**
 * autoRegisterFromManifest — 将 scanner 扫描结果自动注册到 TS 侧
 * 由 Electron main process 启动时调用:
 *   1. bs_biz_scanner_scan("business/") → manifest[]
 *   2. 每个 manifest → bridge.autoRegister()
 *   3. bridge 内部创建 IBusinessAdapter → BusinessAdapterRegistry.register()
 */
export function autoRegisterFromManifest(manifests: ManifestJson[]): void {
  for (const m of manifests) {
    const adapter: IBusinessAdapter = {
      id: m.biz_id,
      displayName: m.display_name,
      getFieldDeclarations: () => m.fields.map(f => ({
        key: f.key, type: f.type,
        defaultStr: f.default, description: f.description,
        required: f.required,
      })),
      getAIData: () => ({
        configLabels: Object.fromEntries(
          m.ai_data.config_labels.map(([k, v]) => [k, v])),
        invertedIndex: Object.fromEntries(
          m.ai_data.inverted_index.map(({ keyword, configKeys }) =>
            [keyword, configKeys])),
        domainShards: m.ai_data.domain_shards,
        skillRoutes: m.ai_data.skill_routes,
      }),
      getNormalizer: () => null, // C 侧提供, TS 侧无需归一化
      getSystemPromptIdentity: () => m.display_name,
      getConsultationKnowledge: () => '',
    }
    BusinessAdapterRegistry.register(adapter)
  }
}

# 🏛️ 架构方案选择记录 (ADR) — Gate 失败处方笺

## 1. 需求背景

Gate 链拦截非法配置变更时，当前仅返回 `FAIL + error_message`（如 `font_size must be >= 12`）。用户看到报错不知道如何修改，导致反复试错。要求在报错中附带**可执行的修正建议（处方笺）**，复用 AdaptiveIndex 的缓存命中实现毫秒级响应，陌生错误走 AI 管线生成建议并做 Dry-Run 预校验。

## 2. 三大候选方案对比

| 维度 | 方案A (极简适配器层) | 方案B (联动 AI 管线) ⬅️ **已选中** | 方案C (内核级增强) |
| :--- | :--- | :--- | :--- |
| **核心思路** | Adapter 层拦截 gate 失败结果，插桩结构化错误码 + 静态预置建议 | 全链路整合：gate 失败 → Adapter 拦截 → 查 AdaptiveIndex / 调 LLM → 推送建议到前端 | 在 kernel gate_chain 中加 suggestion 字段，统一输出结构 |
| **建议来源** | 仅 `error_fingerprint → 静态修正表`（硬编码 JSON） | `AdaptiveIndex` 缓存 + `LLM` 双源，含 Dry-Run | 随 gate DAG 节点预注册 `suggest_fn` 回调 |
| **优点** | 改动最小，0 额外依赖 | 智能兜底，冷启动走 LLM、热命中走缓存（毫秒级），用户越用越准 | DAG 原生支持，gate 规则编写者能直接内嵌修正逻辑 |
| **缺点** | 无法覆盖未知错误，维护静态表成本高 | 需新增 `SuggestionGenerator` 模块 + LLM 调用 + Dry-Run 管线 | 污染 kernel 纯引擎职责，破坏分层 |
| **适应性学习** | 无 | ✅ 自动：用户手动改对 → 记录指纹 → 下次命中 | 需 gate 编写者手动配 `suggest_fn` |
| **LLM 调用** | ❌ 从不 | ✅ 仅冷启动/新指纹 | ❌ 从不 |
| **新增模块** | 0 | 1 个 `SuggestionGenerator` (C++) + 前端 `SuggestionRenderer` | 扩充 `bs_gate_node_t` |
| **涉及改动层** | Adapter 层 | Adapter + SDK + Editor（前端） | Kernel + Adapter + SDK + Editor |
| **预估延迟(缓存命中)** | <1ms | <2ms | <1ms |
| **预估延迟(LLM 路径)** | N/A | 2-5s（LLM + Dry-Run） | N/A |
| **维护成本** | ⭐ | ⭐⭐⭐ | ⭐⭐ |

### ⚙️ 架构不变量（审查红线）

1. **Kernel 零侵入**：gate_chain kernel 不可感知 LLM/Suggestion/AdaptiveIndex，其 `bs_gate_eval_result_t` 结构体不可新增 suggestion 字段
2. **SuggestionGenerator 只读原则**：建议生成模块**不可直接写配置**，必须返回 `Suggestion[]` 让用户/前端决定是否应用
3. **Dry-Run 是强制前置信道**：AI 生成的建议在推送给用户前，必须经过 Gate 预校验（复用 GATE 阶段但不 PERSIST）
4. **指纹不可逆**：`error_fingerprint` 仅做匹配 key，不包含配置值明文，避免缓存泄露敏感数据
5. **AdaptiveIndex 双向隔离**：NLU 路由（现有 key 空间）和错误修正建议（新增 `fix:` 前缀 key 空间）共用存储引擎但隔离

# 🏛️ 架构方案选择记录 (ADR) — blessstar 契约开发工作流设计

## 1. 需求背景

业务系统接入 BlessStar 当前依赖手写 `bs_config_declare` + 手写 gate 函数 + 手写 manifest.json + 手写注册胶水。新人接入需翻阅 4 份头文件、理解 3 种注册入口，门槛极高。且这些基础设施全部是 C 接口，但业务系统可能是任意语言（Rust/Go/Python/Java 等），C 接口对非 C 业务系统不友好。

### ⚙️ 架构不变量（审查红线）

1. **契约文件即真相**：`contract.yaml` 是业务系统的唯一元数据入口。`manifest.json` 应为 `contract.yaml` 的编译产物（由 `blessstar spec` 顺带生成），**禁止手写 manifest.json**
2. **落地建议只建议不代劳**：`blessstar spec` 永远不可直接修改业务代码（不写任何语言的源文件）。落地建议只是文档，代码必须由 LLM + 人工 review 生成
3. **Gate 逻辑不可完全自动生成**：`contract.yaml` 的 `gates[].rule` 只作描述性声明，具体 gate 函数核心判断逻辑必须手写。LLM 生成的 gate 骨架可通过，但 `out->accepted` 判断逻辑必须人工审核
4. **LLM 输出可编译可验证**：LLM 输出的代码必须能通过目标语言的构建系统验证（C→cmake、Rust→cargo、Go→go build、Python→pytest 等）。违反此条直接打回
5. **契约格式向前兼容**：`contract.yaml` 新增字段必须 optional（带 default），禁止删除已有字段，禁止更改已有字段的类型
6. **业务系统语言不绑定基础设施语言**：BlessStar C kernel 是基础设施，业务系统可选用任何语言实现 gate/effect 逻辑。连接方式可以是 FFI shim、子进程调用、或只通过 manifest.json 做元数据注册（gate/effect 可选延后实现）

# 🏛️ 架构方案选择记录 (ADR) — blessstar 多语言业务系统集成方案

## 1. 需求背景

`contract.yaml` 是语言无关的，但运行时的 gate 校验和副作用回调是 C 函数指针（`ReloadPathGateFn`、`bs_runtime_sync_fn`）。Python/Go/Rust/Java 等语言的业务系统无法直接注册这些 C 回调。需要定义一套多语言集成方案，让非 C 业务系统也能参与 Commit 管线的 gate/effect 生命周期。

## 2. 三大候选方案对比

| 维度 | 方案A (纯元数据) | 方案B (Hybrid FFI) ⬅️ **已选中** | 方案C (IPC 桥接) |
| :--- | :--- | :--- | :--- |
| **核心思路** | 业务系统只提交 contract.yaml，简单 gate（range/enum/format）由 kernel DAG 编译器自动处理。不提供自定义 gate/effect 能力 | **分层集成：简单 gate → kernel DAG 自动处理；复杂 gate/effect → FFI shim 包装目标语言函数。`blessstar spec --lang=x` 生成目标语言特定的 FFI shim 骨架 + 适配器代码** | 业务系统作为独立进程运行，通过 protobuf/gRPC 与 C kernel 交互。gate 校验和副作用执行走 IPC 调用 |
| **业务系统工作量** | 只写 contract.yaml（5 分钟），0 行运行时代码 | **简单场景：0 行代码。复杂场景：写业务语言的门禁逻辑 + 少量 FFI 绑定（由模板生成）** | 写业务语言的 gRPC client + protobuf schema + 进程管理 |
| **Custom gate 支持** | ❌ 不支持（仅限 kernel 内置规则） | **✅ 支持（FFI shim 回调目标语言）** | ✅ 支持（IPC 调用目标语言进程） |
| **Effect 支持** | ❌ 不支持 | **✅ 支持（FFI shim，适合轻量级副作用）** | ✅ 支持（IPC，适合重量级副作用） |
| **Gate 延迟** | <1μs（纯 C DAG） | **<10μs（FFI 跨语言调用栈）** | >1ms（IPC 序列化 + 进程切换） |
| **部署复杂度** | ⭐ 最低 | **⭐⭐（需编译 FFI 共享库）** | ⭐⭐⭐⭐（需管理业务系统进程） |
| **适用场景** | 纯声明型业务（仅 range 校验） | **中等复杂度，需自定义校验逻辑** | 门禁逻辑重、有独立部署诉求 |
| **实现成本** | 0 新增 | **5 人天（FFI shim 模板 + C kernel 侧注册 API 扩展）** | 4 周（IPC 协议 + 连接管理） |

## 3. 用户最终确认草案（标注日期）

> **确认选择**：方案B — Hybrid FFI（分层集成：简单规则 → kernel DAG 自动处理；复杂逻辑 → FFI shim 包装目标语言函数）
>
> * **核心分层结构**：
>   - **L0 — kernel DAG 自动编译**：`sub_category=threshold|format|enum_check` 的简单规则由 `bs_gate_ast_compile` 从 contract.yaml 自动编译为 DAG 节点，业务系统不需要写任何 gate 代码
>   - **L1 — contract.yaml 注册声明**：业务系统通过 `contract.yaml` 声明字段、依赖、gate 规则和 effect 意图，`blessstar spec` 编译出 `manifest.json`，由 C kernel 在启动时加载并注册
>   - **L2 — FFI shim 桥接**：`sub_category=alert|approval|custom` 的复杂 gate/effect 通过 FFI shim 回调目标语言。`blessstar spec generate --lang=x` 自动生成 shim 骨架
>

### ⚙️ 架构不变量（审查红线）

1. **L0 gate 不可为 L2 写代码**：`sub_category=threshold|format|enum_check` 的 gate 规则由 kernel `bs_gate_ast_compile` 自动从 `contract.yaml` 编译为 DAG 节点。业务系统**不允许也不需要在 ffi_shim 中重复实现这些规则**
2. **FFI shim 由模板生成，不手工写**：FFI 绑定代码（`extern "C"`、`#[no_mangle]`、`ctypes.CFUNCTYPE`、`cgo` 等）由 `blessstar spec generate --lang=x` 自动输出。开发者**只允许修改 shim 内部调用的业务逻辑函数**，不允许修改 FFI 边界签名
3. **Shim 生命周期绑定 kernel**：FFI shim 编译为 `.dll/.so/.dylib`，由 C kernel 在 `module_init` 时通过 `dlopen`/`LoadLibrary` 动态加载。业务系统不需要链接到 BlessStar 二进制，kernel 崩溃不影响 shim 进程（事实上 shim 在 kernel 进程内）
4. **解释型语言允许无编译步骤**：Python 等解释型语言的 FFI shim 模板使用 `ctypes.CDLL`/`cffi.FFI` 直接加载 kernel 导出符号，不需要编译 C 扩展，只需要运行时解释器。编译型语言（Rust/Go/Java C#/TS napi）需要目标语言的编译器工具链，模板会同时生成对应语言的构建配置（`Cargo.toml`/`go.mod`/`pom.xml`/`.csproj`/`package.json`）
5. **manifest.json 是唯一注册凭证**：`blessstar spec` 产出的 `manifest.json` 包含所有 L0/L1 注册信息（不含 L2 shim 路径，shim 路径由 `blessstar spec` 另行生成注册配置）。启动时 kernel 扫描 `biz/*/manifest.json` 完成注册，不依赖业务系统进程是否存活

2. 配置 Key 散落在业务代码各处 — 无类型安全，无编译期校验
3. 业务语义缺失 — 代码中充斥 `/config/payment/timeout` 这样的路径字符串，而非 `paymentConfig.GetTimeout()` 这样的业务语义

升级目标：引入**端口-适配器模式**，在不拆除现有统一注册体系的前提下，在业务系统代码侧增加一层接口膜。

同时发现几个生产级缺陷，一并修复：
- **无容灾降级** — BlessStar 宕机 → `GetTimeout()` 返回 0 → 业务系统灾难性故障
- **无链路追踪** — 方法签名缺少 `context.Context`，审计排障断裂
- **依赖注入手写维护成本高** — 服务增多时 main.go 膨胀

# 🏛️ 架构方案选择记录 (ADR) - 移除 blessstar-sdk-go 外部依赖，采用 ConfigReader 接口注入

## 1. 需求背景

当前 blessstar-codegen 生成的 Go 适配器代码依赖 `blessstar-sdk-go` 外部包，该包目前仅作为空桩存在（`Client.Get()` 返回 `(nil, nil)`），无运行时价值。同时，生成的 Port 接口直接引用 `*blessstar.Client` 类型，违反了"Port 不得依赖外部 SDK"的架构不变量。

核心问题：Go 业务系统如何读取 BlessStar C++ 共享内存中的配置？需要一个**零外部依赖、配置源可插拔、生成代码即开即用**的方案。

## 2. 三大候选方案对比

| 维度 | 方案A (极简运维) | 方案B (高性能) | 方案C (高扩展) |

| **核心思路** | `ports/` 中定义 `ConfigReader` 接口，去掉外部 SDK 依赖；业务方自行决定配置源实现 | cgo 封装 BlessStar C++ SHM 读出端，Go 直接读共享内存 | BlessStar 启动 sidecar 进程暴露 gRPC ConfigService |

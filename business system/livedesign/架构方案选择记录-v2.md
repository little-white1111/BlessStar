## 1. 需求背景

### 1.1 业务描述

**livedesign** 是一个面向直播主播和 OBS 用户的**直播间样式可视化设计器**。用户通过拖拽、缩放等可视化操作，在画布上自由排列和配置直播间组件（弹幕列表、背景、音乐歌词、打赏动画等），实时预览效果，并通过 obs-websocket 将配置推送到 OBS，或导出配置文件供 OBS 独立加载。

### 1.2 核心功能清单

| # | 功能 | 描述 | 优先级 |
|:-|:-----|:-----|:------:|
| F1 | 可视化画布编辑器 | 基于 React 的拖拽/缩放/自由布局画布 | P0 |
| F2 | 组件化样式系统 | 弹幕列表、背景、音乐歌词等组件，可独立开发、可插拔加载 | P0 |
| F3 | 图层管理 | PS 式图层层级（z-index）、显隐切换、锁定 | P0 |
| F4 | 属性面板 | 选中组件后配置其样式参数（颜色、字体、位置、动画等） | P0 |
| F5 | OBS 集成 | 双向：实时通过 obs-websocket 推送配置 + 导出文件供 OBS 读取 | P1 |
| F6 | 组件配置本地存储 | 存放在 `~/livedesign/components/` 目录，每个组件一个配置文件 | P1 |

### 1.3 非功能性需求

| 类型 | 需求 | 约束 |
|:-----|:-----|:-----|
| 性能 | 无组件数量限制，画布需实时渲染 | WebGL/Canvas 加速，虚拟列表/脏矩形 |
| 热更新 | 运行时热更新，不刷新页面即可调整配置 | 文件监听 → 配置变更 → 实时生效 |
| 架构 | 纯前端应用 + 本地文件系统存储 | 无后端服务，Electron/Web 均可 |
| 配置 | 走 BlessStar 配置加载链路 | Schema 验证 + 文件监听热更新 |
| 团队 | 单人开发 | 架构需简洁，减少认知负荷 |
| 阶段 | Phase 1 | 配置字段暂未确定，留待后续 configdesigner 提取 |

## 2. 三大候选方案对比

| 维度 | 方案A（极简运维） | 方案B（均衡架构）⬅️ **推荐** | 方案C（高扩展） |
|:-----|:------------------|:---------------------------|:----------------|
| **核心思路** | 单体 React 应用，所有功能内聚，直接操作文件系统 | 分层模块化，编辑器与组件引擎分离，BlessStar 管理配置 | 微前端 + 插件沙箱，事件总线解耦，多渲染目标 |
| **架构风格** | 单体 SPA (React) | 分层模块化 (Modules + Port/Adapter) | 微前端 (Module Federation + Event Bus) |
| **组件加载机制** | React 组件直接 import | Web Components 包装层（框架无关） | Web Components + 沙箱隔离 + 版本管理 |
| **配置治理深度** | 无（本地 JSON/YAML 文件，手动编辑） | 中（BlessStar Schema 验证 + 文件监听热更新） | 深（BlessStar 全生命周期 + 门禁 + 降级策略） |
| **OBS 集成方式** | 应用内直接连接 obs-websocket | obs-bridge 独立模块，支持实时推送 + 文件导出 | obs-bridge + OBS Browser Source 预览 + 双向同步 |
| **模块边界** | 无（按文件夹组织） | 4 个独立模块，接口契约定义 | 每个组件类型为独立微应用 |
| **优点** | • 开发最快（1人2周可出 MVP）<br>• 认知负荷最低<br>• 无需学习额外概念 | • 模块边界清晰，易于并行开发<br>• Web Components 包装支持未来框架迁移<br>• BlessStar 配置管理保证变更安全<br>• 画布与组件引擎分离提升渲染性能 | • 组件可独立部署/升级<br>• 插件沙箱保障安全性<br>• 多渲染目标（Web/OBS/移动端）<br>• 扩展性最强 |
| **缺点** | • 无法框架无关加载组件<br>• 配置变更无验证，易出错<br>• 画布渲染与 UI 逻辑耦合，大组件量时性能堪忧<br>• 无模块边界，长期维护困难 | • 需学习 Web Components + BlessStar 配置<br>• 初期搭建需一定时间<br>• 单人开发可能感觉"过度设计" | • 微前端架构复杂度过高<br>• 单人团队无法维护<br>• 事件总线增加调试难度<br>• 绝大多数功能为过度设计 |
| **预估工作量** | 2-3 周 (1人) | 6-8 周 (1人) | 12-16 周 (1-2人) |
| **维护成本** | ⭐⭐（初期低，后期快速上升） | ⭐（初期中，长期稳定） | ⭐⭐⭐（持续高） |
| **BlessStar 影响** | 无（纯文件存储） | config-schema.yaml + codegen + 文件监听 | config-schema.yaml + 门禁 + 降级 + 事件触发 |
| **适用场景** | 仅用于个人临时测试 | **生产级直播间设计器** | 大型直播平台内嵌设计器 |

## 3. 推荐方案论证

### 选择方案B（均衡架构）

#### 理由

1. **模块边界化解耦合**：livedesign 的核心矛盾在于"画布编辑器"与"组件运行时引擎"的生命周期不同——画布需要高频交互事件（拖拽/缩放/选中），组件引擎需要高效渲染（实时视频/动画）。方案A 将两者耦合在一起，当组件数量增加时必然出现渲染卡顿。方案B 通过 Web Components 包装层将两者解耦，组件引擎独立运行，不受 React 重渲染影响。

2. **BlessStar 配置管理是刚需**：用户的非功能性需求明确要求"走 BlessStar 配置加载链路（Schema 验证 + 文件监听热更新）"。方案A 无法满足此需求，方案C 又引入过多配置治理能力（门禁、降级、事件触发），对于 Phase 1 的单人团队而言过度了。方案B 恰好匹配——使用 BlessStar 的 Schema 验证确保配置正确性，文件监听实现热更新，但不强制使用门禁等高级特性。

3. **Web Components 包装层提供框架无关性**：直播间组件可能由不同开发者使用不同框架编写（React/Vue/原生 JS）。方案B 的 Web Components 包装层提供了框架无关的组件加载能力，同时为未来的组件市场/插件生态奠定基础。

4. **单人团队友好**：方案B 的 4 个模块（editor/engine/plugin-sdk/obs-bridge）的边界恰好对应 4 个独立关注点，单人开发可依次推进（先 editor+engine，再 plugin-sdk，最后 obs-bridge），每个阶段都有可交付成果。

5. **不是 A 也不是 C 的理由**：
   - **非方案A**：方案A 虽然 MVP 快，但缺少 BlessStar 配置验证、框架无关加载、模块分离这三个关键需求。长期来看，没有模块边界的单体应用在功能膨胀后（图层管理 + 属性面板 + OBS 集成 + N 个组件类型）将迅速失控。
   - **非方案C**：方案C 的微前端架构（Module Federation）和插件沙箱对于单人开发的 Phase 1 而言是沉重的技术和运维负担。事件总线的调试复杂度也不适合早期快速迭代。

#### 技术决策汇总

| 决策点 | 选择 | 理由 |
|:-------|:-----|:------|
| 编辑器框架 | React + TypeScript | 用户明确要求 |
| 组件加载 | Web Components 包装 | 框架无关，支持未来生态 |
| 配置管理 | BlessStar Schema + 文件监听 | 满足 NFR，匹配 Phase 1 |
| OBS 集成 | 独立 obs-bridge 模块 | 与编辑器逻辑解耦 |
| 本地存储 | ~/livedesign/components/ 每组件独立文件 | 明确指定 |
| 状态管理 | Zustand（轻量） | 比 Redux 简单，比 Context 高效 |
| 通信模式 | 自定义事件 (CustomEvent) | 模块间解耦，Web Components 原生支持 |

## 5. 架构不变量（审查红线）

以下为架构级不可妥协的规则，任何代码变更不得违反：

| # | 不变量 | 严重度 | 说明 | 验证方式 |
|:-:|:-------|:------:|:------|:---------|
| I1 | **画布编辑器与组件运行时引擎必须运行在独立的执行上下文中** | 🔴 红线 | 编辑器（React 重渲染循环）与组件引擎（实时渲染循环）共享同一线程会导致帧率下降。必须通过 Worker / iframe / 子进程隔离。 | 性能测试：10 个组件同时存在时，画布拖拽帧率 ≥ 30fps |
| I2 | **组件配置变更必须经过 BlessStar Schema 验证** | 🔴 红线 | 任何写入 `~/livedesign/components/` 的 YAML 文件必须先经 Schema 校验，拒绝非法配置。不允许绕过验证直接写文件。 | 集成测试：写入非法字段 → 验证被拒绝 |
| I3 | **组件必须通过 Web Components 标准接口加载** | 🟡 重要 | 所有组件必须实现标准的 Web Components 生命周期（`connectedCallback` / `disconnectedCallback` / `attributeChangedCallback`），不得直接依赖 React 生命周期。 | 类型测试：验证每个组件注册为 `customElements.define()` |
| I4 | **组件配置以独立文件存储，不汇聚为单一配置文件** | 🟡 重要 | 每个组件的配置存储在 `~/livedesign/components/<name>/component.yaml`，不得将所有组件配置合并写入一个文件。 | 架构测试：验证写操作路径格式 |
| I5 | **OBS 集成必须是可选的，不得阻塞编辑器主流程** | 🔴 红线 | OBS 连接失败/不可用不应影响画布编辑功能。obs-bridge 模块的故障不得传播到编辑器或组件引擎。 | 故障注入测试：断开 OBS → 验证编辑器正常操作 |
| I6 | **文件变更（外部编辑）必须触发组件热更新** | 🟡 重要 | BlessStar 文件监听检测到 `component.yaml` 变更后，必须重新验证 Schema 并通知 ComponentEngine 更新渲染。 | 集成测试：外部修改文件 → 验证组件自动重渲染 |
| I7 | **禁止组件间直接耦合通信** | 🔴 红线 | 组件之间不得通过 import/引用直接调用。必须通过 ComponentEngine 的 EventBus 或配置变更间接通信。 | 架构测试：静态分析 import 路径 |
| I8 | **组件 SDK（plugin-sdk）必须零依赖打包** | 🟡 重要 | `livedesign-plugin-sdk/` 导出的类型和工具函数不得依赖 React 或任何 UI 框架，仅依赖原生 Web API + TypeScript。 | 构建测试：验证 SDK 的 bundle 中无 React |
| I9 | **图层管理与渲染顺序必须解耦** | 🟡 重要 | 图层的 z-index/显隐/锁定状态由编辑器侧的 LayerManager 维护，组件引擎只消费最终的排序和可见性列表，不持有图层逻辑。 | 单元测试：验证 engine 无 LayerManager 引用 |
| I10 | **配置导出格式必须版本化** | 🔴 红线 | 所有导出的 OBS 配置文件和组件配置文件必须携带 `version` 字段，支持向前兼容读取旧版本格式。 | 兼容性测试：加载 v1.0 格式 → 验证可正常解析 |
| I11 | **单向数据流：编辑器 → ComponentEngine → 组件实例** | 🟡 重要 | 状态变更方向：编辑器 →（通过 IPC）→ ComponentEngine →（通过属性赋值）→ Web Components 实例。不允许组件实例直接修改编辑器状态。 | 架构测试：验证组件实例无 store 引用 |

## 11. 降级策略

| 场景 | 降级路径 | 行为 |
|:-----|:---------|:-----|
| BlessStar Sidecar 不可用 | `ConfigManager` 降级到本地 JSON 直读 | 失去 Schema 验证和热更新能力，但基础编辑功能正常 |
| OBS 连接失败 | `obs-bridge` 进入 `disconnected` 状态，定时重连 | 编辑器正常，OBS 推送按钮禁用，显示断连提示 |
| 组件引擎 Worker 崩溃 | 自动重启 Worker，编辑器显示 "组件引擎重启中" | 编辑器 UI 不受影响，组件配置等待引擎恢复后同步 |
| 单个组件加载失败 | `ComponentRegistry` 跳过该组件，其余组件正常 | 编辑器跳过该组件注册，显示占位符 "组件加载失败" |
| Schema 验证失败 | 写操作被拒绝，编辑器显示验证错误详情 | 配置不写入文件，用户根据错误提示修正后重试 |

# 架构方案选择记录 — resumedesign

> **版本**: v1.0
> **日期**: 2026-07-13
> **状态**: 骨+肉完成（Phase 1 + Phase 2），活血（Phase 3）已跳过，可后续接入 BlessStar

---

## 1. 业务背景

resumedesign 是一个简历智能改写系统。用户上传原始简历（PDF/DOCX/纯文本），从招聘 URL 或 API 获取岗位要求（JD），系统调用 LLM（GPT/Claude）将原简历针对 JD 进行适当改写，保留核心信息的同时贴合岗位要求。

- **目标用户**: 国内求职者（中文）
- **部署形态**: Web（前后端分离）+ CLI
- **性能预期**: 个人工具，低并发
- **AI 模型**: LLM API（GPT/Claude）
- **数据策略**: 原始简历持久化本地做模板，LLM 调用时从 KV 缓存读取原始简历+岗位要求

## 2. 架构方案选择

### 三方案对比

| 维度 | 方案A（极简运维） | 方案B（均衡架构）⭐ | 方案C（高扩展） |
|:-----|:-----------------|:------------------|:---------------|
| **核心思路** | 单体聚合，JSON 文件即数据库 | Port-Adapter 六边形架构，SQLite | 事件驱动管道，PgSQL+Redis+MinIO |
| **技术栈** | Go stdlib + JSON 文件 | Go + GORM/SQLite + Gin | Go + GORM/PgSQL + Redis + NATS |
| **配置治理** | 无 Schema | Phase 2 本地 config | Phase 3 远程配置中心 |
| **部署形态** | 单二进制 | 单二进制 + SQLite | Docker Compose / K8s |
| **启动时间** | 2-3 天 | 5-7 天 | 10-14 天 |
| **维护成本** | ★☆☆☆☆ | ★★☆☆☆ | ★★★★☆ |

### 选定方案：方案B（均衡架构）

**选择理由：**
1. 个人工具、低并发，方案C 过度设计
2. Port-Adapter 结构与 Phase 1 产出物天然对齐
3. Web + CLI 共享 internal 层，零代码重复
4. 预留 `adapter/blessstar/` 目录，Phase 3 可零侵入接入
5. SQLite 单文件满足全部持久化需求

## 6. 架构不变量（12 条）

### 业务不变量（7 条）

| # | 不变量 | 类型 |
|:-:|--------|:----:|
| 1 | 原始简历作为不可变模板，改写操作永不修改原始简历 | 数据完整性 |
| 2 | 项目经历、成就奖项、专业技能方向三类核心信息不可被 LLM 丢弃或扭曲 | 内容保真 |
| 3 | 个人身份信息（姓名、联系方式、邮箱）不可被 LLM 修改 | 数据安全 |
| 4 | 同一份原始简历可对应多个 JD 产生多个独立改写版本 | 版本管理 |
| 5 | 每次 LLM 调用必须记录 model、temperature、prompt 摘要，确保可审计 | 可追溯性 |
| 6 | 改写结果必须包含差异标注，用户不可接受无痕修改 | 透明度 |
| 7 | JD 来源 URL 必须经过有效性校验，失败时降级为用户手动粘贴 | 鲁棒性 |

### 技术不变量（5 条）

| # | 不变量 | 违反后果 |
|:-:|--------|---------|
| T1 | 所有 LLM 调用必须经过 `port.LLMClient` 接口，禁止在 service/domain 中直接发起 HTTP 请求到 LLM | 无法切换模型、无法审计、无法 mock 测试 |
| T2 | 简历解析器、JD 抓取器、导出器必须实现 port 层接口，service 层只依赖接口，不依赖具体 adapter | 替换实现需修改业务代码，违反 DIP |
| T3 | 配置读取必须通过 `port.ConfigReader` 接口，禁止 `os.Getenv` / `flag` 散落在业务代码中 | 配置来源不可控，迁移到 Phase 3 Schema 时需大面积重构 |
| T4 | `RewriteSession` 每次状态变更必须持久化到数据库，不允许仅存在于内存 | 进程崩溃导致改写任务丢失，不可恢复 |
| T5 | 文件导入导出操作的临时文件必须通过临时目录管理，禁止在工作目录下随意创建 | 部署目录污染，容器环境下权限异常 |

## 7. 技术栈选型

| 层次 | 选型 | 理由 |
|------|------|------|
| 语言 | Go 1.22+ | 单二进制、跨平台、CLI+Web 天然优势 |
| Web 框架 | Gin | 轻量、成熟、REST API 首选 |
| ORM | GORM + SQLite driver (mattn/go-sqlite3) | 个人工具无需独立数据库 |
| PDF 解析 | pdfcpu | 纯 Go、无 CGO、开源活跃 |
| DOCX 解析 | 自建 (go-docx / ZIP+XML 解析) | DOCX 本质是 ZIP+XML，自建可控 |
| LLM 客户端 | 直接 HTTP（指数退避重试） | 无外部 SDK 依赖，代码可控 |
| CLI 框架 | cobra + pflag | Go 生态 CLI 事实标准 |
| 前端 | Vue 3 + Vite + TypeScript | 与 livedesign 技术栈一致 |
| KV 缓存 | 基于 SQLite 的 KV 表 | 复用已有 SQLite，不引入 Redis |

## 8. 数据 Schema 设计

```sql
-- resumes 简历表
CREATE TABLE resumes (
    id            TEXT PRIMARY KEY,         -- UUID v7
    title         TEXT NOT NULL,            -- 简历标题/文件名
    raw_content   TEXT NOT NULL,            -- 解析后的纯文本内容
    import_format TEXT NOT NULL,            -- pdf | docx | txt
    created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_resumes_created_at ON resumes(created_at);

-- sections 简历段落表
CREATE TABLE sections (
    id            TEXT PRIMARY KEY,         -- UUID v7
    resume_id     TEXT NOT NULL REFERENCES resumes(id) ON DELETE CASCADE,
    section_type  TEXT NOT NULL,            -- personal | education | work | project | skill | award
    title         TEXT NOT NULL DEFAULT '',
    content       TEXT NOT NULL DEFAULT '',
    sort_order    INT NOT NULL DEFAULT 0,
    created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_sections_resume_id ON sections(resume_id);
CREATE INDEX idx_sections_resume_order ON sections(resume_id, sort_order);

-- job_descriptions 岗位要求表
CREATE TABLE job_descriptions (
    id            TEXT PRIMARY KEY,         -- UUID v7
    source        TEXT NOT NULL,            -- url | api | manual
    source_url    TEXT,
    company       TEXT NOT NULL DEFAULT '',
    position      TEXT NOT NULL DEFAULT '',
    raw_content   TEXT NOT NULL,
    created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- rewrite_sessions 改写会话表
CREATE TABLE rewrite_sessions (
    id               TEXT PRIMARY KEY,     -- UUID v7
    resume_id        TEXT NOT NULL REFERENCES resumes(id) ON DELETE CASCADE,
    jd_id            TEXT NOT NULL REFERENCES job_descriptions(id) ON DELETE CASCADE,
    status           TEXT NOT NULL DEFAULT 'draft',  -- draft | processing | completed | failed
    model            TEXT NOT NULL DEFAULT '',
    temperature      REAL NOT NULL DEFAULT 0.7,
    rewritten_content TEXT NOT NULL DEFAULT '',
    prompt_hash      TEXT NOT NULL DEFAULT '',
    error_message    TEXT NOT NULL DEFAULT '',
    created_at       DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    completed_at     DATETIME
);
CREATE INDEX idx_sessions_resume_id ON rewrite_sessions(resume_id);
CREATE INDEX idx_sessions_status ON rewrite_sessions(status);

-- diffs 差异表
CREATE TABLE diffs (
    id                TEXT PRIMARY KEY,    -- UUID v7
    session_id        TEXT NOT NULL REFERENCES rewrite_sessions(id) ON DELETE CASCADE,
    section_type      TEXT NOT NULL,
    original_content  TEXT NOT NULL DEFAULT '',
    rewritten_content TEXT NOT NULL DEFAULT '',
    change_type       TEXT NOT NULL,        -- modified | added | removed | unchanged
    confidence        REAL NOT NULL DEFAULT 1.0,
    sort_order        INT NOT NULL DEFAULT 0
);
CREATE INDEX idx_diffs_session_id ON diffs(session_id);
```

## 11. 可变参数与配置治理

### 可变参数候选（7 个）

| key | type | default | 业务描述 |
|-----|------|---------|---------|
| llm.model | STR | gpt-4o | LLM 模型选择 |
| llm.temperature | FLOAT | 0.7 | 改写创造性程度（0~1） |
| rewrite.max_length | INT | 1000 | 改写后简历最大字数 |
| rewrite.section_order | STR_LIST | ["个人信息","教育背景","工作经历","项目经历","技能"] | 简历段落排序 |
| cache.ttl | DURATION | 24h | 原始简历 KV 缓存有效期 |
| export.format | STR_LIST | ["pdf","docx"] | 支持的导出格式 |
| jd.crawl_timeout | DURATION | 10s | JD 页面抓取超时时间 |

### 当前治理方式

全部 7 个参数通过 `~/.resumedesign/config.yaml` 本地文件管理，通过 `adapter/config/local.go` 实现 `port.ConfigReader` 接口。

### 后续接入 BlessStar 声明

> 当前方案未启用 BlessStar 配置治理。后续如需接入 BlessStar 动态治理，只需：
> 1. 在 `adapter/` 下新增 `blessstar/` 目录，实现 `port.ConfigReader`
> 2. 在 `provider/wire.go` 中替换 ConfigReader 的实现
> 3. 运行 `blessstar-codegen --schema config-schema.yaml --lang go`
>
> 核心业务代码（`internal/domain/` 和 `internal/service/`）**零改动**。

# 岗位筛选与批量投递架构增强

> **版本**: v1.0
> **日期**: 2026-07-13
> **状态**: 骨+肉完成（Phase 1 + Phase 2），活血（Phase 3）可选，隶属于 resumedesign 的 JD 智能获取与投递管理模块

---

## 1. 设计背景

resumedesign 原有的 JD 获取方式仅为单 URL 抓取 + 手动粘贴文本，缺乏对岗位质量的评估筛选能力。同时，简历改写完成后缺乏批量投递管理和投递缓存过期清理机制。

本次增强设计两个核心模块：

| 模块 | 业务目标 | 核心能力 |
|:-----|:---------|:---------|
| **岗位可信筛选（JDScreening）** | 从多个岗位来源中批量筛选出可靠的、关键词匹配度高的岗位 | 关键词扩展、可信度评分、双阈值过滤 |
| **批量投递管理（BatchDelivery）** | 管理改写后简历的批量投递，控制投递缓存生命周期 | 投递记录、简历导出+文件存储、定时过期清理 |

---

## 2. 架构方案选择

### 2.1 岗位筛选 — 三方案对比

| 维度 | **方案A（轻量集成）** | **方案B（均衡架构）⭐** | **方案C（高扩展）** |
|:-----|:--------------------|:--------------------|:-------------------|
| **关键词扩展** | 硬编码同义词映射 | `port.KeywordExpander` 接口 + 本地 JSON 词典 | 接口 + 远程词典 + 热加载 |
| **可信度评分** | 纯规则硬编码 | `port.TrustScorer` 接口 + 启发式规则 | 接口 + 规则引擎 + 第三方 API |
| **批量搜索** | 不提供 | `port.JDSearchEngine` 接口 + 网页解析 | 接口 + 多平台适配器 |
| **新增文件数** | 3-4 | 10-14 | 18-25 |
| **改动侵入** | 修改 `jd_service.go` | 新增文件为主，零侵入 | 新增文件为主 |

**选定方案B** — 保持与现有 resumedesign 一致的 Port-Adapter 风格。

### 2.2 批量投递 — 三方案对比

| 维度 | **方案A（轻量）** | **方案B（均衡架构）⭐** | **方案C（高扩展）** |
|:-----|:---------------|:--------------------|:------------------|
| **投递记录** | SQLite 硬编码表 | `DeliveryRepo` 接口 + GORM 实现 | 多种后端（MySQL/ES） |
| **文件存储** | 直接写磁盘路径 | `FileStorage` 接口 + local 实现 | 可切换 S3/MinIO |
| **浏览器打开** | `exec.Command` 直调 | `BrowserOpener` 接口 + OS 实现 | 远程浏览器 |
| **定时清理** | 无（手动执行） | `scheduler.CleanupTask` 定时协程 | 分布式 Cron + 事件 |
| **新增文件数** | 3-4 | 10-14 | 20-28 |

**选定方案B** — 独立服务 + Port 接口 + 定时协程清理。

## 6. 架构不变量（追加 10 条）

### 岗位筛选业务不变量（5 条）

| # | 不变量 | 类型 |
|:-:|--------|:----:|
| S1 | **原始 JD 不可修改** — 评分过程中不修改 JD 原始内容（`RawContent` 只读） | 数据完整性 |
| S2 | **评分可复现** — 相同输入条件下评分结果一致（确定性评分，不引入随机性） | 可审计性 |
| S3 | **阈值两侧互斥** — 通过和未通过严格基于阈值，不可人工干预跳过筛选 | 业务规则 |
| S4 | **评分明细可追溯** — 每次评分必须记录评分因子明细，未通过必须有原因说明 | 透明度 |
| S5 | **关键词扩展可配置** — 同义词映射表和类别映射表应可动态配置（JSON 词典） | 可维护性 |

### 批量投递业务不变量（5 条）

| # | 不变量 | 类型 |
|:-:|--------|:----:|
| D1 | **投即留痕** — 每次投递操作必须生成持久化记录，不可丢失 | 可追溯性 |
| D2 | **过期必删** — 超过 TTL 的投递记录和文件必须被清理，不可遗漏 | 数据合规 |
| D3 | **文件与记录共存亡** — 有记录必有简历文件；删记录必删文件 | 数据一致性 |
| D4 | **单份简历单次投递** — 同一份简历对同一岗位只允许一次有效投递（过期后重置） | 业务规则 |
| D5 | **TTL 创建锁定** — TTL 在创建时锁定，不允许修改或延长 | 安全约束 |

```sql
-- scoring_sessions 岗位筛选会话表
CREATE TABLE scoring_sessions (

    expire_at         DATETIME NOT NULL
```

## 13. 落地建议

### 落地顺序

1. **Phase 1：Domain 实体** — 创建 `scored_jd.go`、`scoring_session.go`、`delivery_session.go`、`delivery_target.go`
2. **Phase 2：Port 接口** — 定义 5 个新 Port 接口
3. **Phase 3：Repository** — `scoring_repo.go` + `delivery_repo.go`
4. **Phase 4：Adapter 实现**
   - `scorer/heuristic.go` — 规则引擎：薪资检测、福利检测、位置匹配
   - `keyword/expander.go` + `keyword/dict.go` — 同义词/类别词典
   - `search/webpage.go` — 招聘网页搜索结果页解析
   - `filestorage/local.go` — 文件系统存取代
   - `browser/opener.go` — 跨平台浏览器打开
5. **Phase 5：Service 编排** — `screening_service.go` + `delivery_service.go`
6. **Phase 6：Scheduler** — `scheduler/cleanup.go` 定时清理
7. **Phase 7：入口集成** — `cmd/server/main.go` 新增路由 + `cmd/cli/main.go` 新增命令
